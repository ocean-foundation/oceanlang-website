=== source
group: Contribute
title: Source code
desc: Where the compiler, standard library, and this website are developed.

--- repositories | The three repositories
Ocean is developed in the open on GitHub, in three repositories under the `ocean-foundation` organization.

`ocean` holds the compiler, written in Ocean, together with the language server, the installer, the release scripts, the editor support files, and the compiler's test suite. See `ocean-c` for the legacy compiler written in C.

`ocean-src` holds the standard library, written in Ocean. A compiler release and the library tag with the same name belong together.

`oceanlang-website` holds this website and its documentation.
@links
ocean-foundation/ocean -> https://github.com/ocean-foundation/ocean
ocean-foundation/ocean-src -> https://github.com/ocean-foundation/ocean-src
ocean-foundation/oceanlang-website -> https://github.com/ocean-foundation/oceanlang-website
ocean-foundation/ocean-c (legacy C compiler) -> https://github.com/ocean-foundation/ocean-c

--- contributing | Making a contribution
Contributions are made as pull requests against each repository's `main` branch. Describe what you changed and which tests you ran. A language change usually touches more than one repository: the compiler, the standard library if it uses the change, and these docs. The compiler repository's agent skill file, `skills/ocean/SKILL.md`, is kept in step with the language and should be updated in the same change.

=== contribute/compiler
group: Contribute
title: Working on the compiler
desc: Build the compiler, run it against a library checkout, find your way around the pipeline, and run its tests.

--- build | Build a development compiler
Follow the source build on the getting-started page: clone `ocean` and `ocean-src` side by side and build with `make`. Building requires an installed bootstrap `ocean` compiler (with a matching standard library), Clang, libffi development headers, `pkg-config`, Git, and GNU Make. The build produces `build/ocean`, and `make selfhost` compiles the compiler with itself to produce `build/ocean-stage2`. Rebuild with `make` after changing source files.
```code Terminal
make
make selfhost
```
@after
Override the bootstrap compiler or version with `make OCEAN=/path/to/ocean VERSION=1.2.3` (defaults to `ocean` on `PATH` and `dev`). If you edit any of the C runtime files in `compiler/runtime/`, run `make runtime` (or `make`, which runs it automatically) to regenerate `compiler/runtime/source.oc`. `make clean` removes the `build/` directory.

--- run | Run it against your library checkout
A compiler in the build directory has no installed library next to it, so point `OCEAN_SRC` at your `ocean-src` checkout. Setting `OCEAN_BUILD_CACHE=off` makes sure every run really exercises the compiler you just built, rather than reusing cached objects.
```code Terminal
export OCEAN_SRC="$PWD/../ocean-src"
OCEAN_BUILD_CACHE=off build/ocean check /path/to/example
```

--- pipeline | How the compiler is organized
The compiler is written in Ocean, with its entry point in `main.oc` and packages under `compiler/`. A build passes through these stages:
@table
Stage | Main packages
CLI, build driver, linking, cache, test runner, `fetch`, and targets | `main.oc`, `compiler/driver/` (`cli.oc`, `build.oc`, `link.oc`, `cache.oc`, `test.oc`, `fetch.oc`, `target.oc`)
Module and package loading, `ocean.mod`, and `ocean.sum` verification | `compiler/loader/` (`loader.oc`, `sum.oc`)
Scanning source text into tokens | `compiler/scanner/` (`scanner.oc`, `float.oc`, `unicode.oc`)
Parsing tokens into an abstract syntax tree | `compiler/parser/`, `compiler/ast/`
Name resolution, type checking, generics, and layout | `compiler/check/` (`checker.oc`, `resolve.oc`, `expr.oc`, `stmt.oc`, `generic.oc`, `layout.oc`)
Generating LLVM IR | `compiler/backend/` (`gen.oc`, `module.oc`, `func.oc`, `stmt.oc`, `expr.oc`, `expr2.oc`, `call.oc`, `ops.oc`, `desc.oc`)
Runtime support embedded in programs | `compiler/runtime/` (`core.c`, `ffi.c`, `process.c`, `threads.c`, `wasm.c`, generated `source.oc`)
Language server, `ocean fix`, diagnostics, and shared utilities | `compiler/lsp/`, `compiler/fix/`, `compiler/diag/`, `compiler/util/`
@after
The backend writes LLVM IR as text, and `compiler/driver/link.oc` runs Clang to compile and link it. Small Ocean build helpers in `tools/` (`embedruntime` and `embedlogo`) regenerate the embedded runtime and ASCII logo sources during `make`.

--- tests | Tests
`make test` builds `build/ocean` and runs the Ocean unit test suite across every package in the repository (`build/ocean test ./... --notty`). Tests live next to the code they exercise in `*_test.oc` files under `compiler/scanner`, `compiler/parser`, `compiler/check`, `compiler/loader`, `compiler/runtime`, and `compiler/util`. You can also run a single package's tests while working, or verify self-hosting and cross-target IR assembly:
```code Terminal
make test
OCEAN_SRC="$PWD/../ocean-src" build/ocean test compiler/check --notty
make selfhost
make crosscheck
```
@after
When fixing a bug, add a `_test.oc` test in the relevant package that fails without the fix. For changes that affect code generation or runtime behavior, also run `make selfhost` and test against `ocean-src` (`ocean test ./... --notty`) to verify the compiler end to end.

=== contribute/stdlib
group: Contribute
title: Working on the standard library
desc: How the standard library is laid out, how to test changes, and the conventions packages follow.

--- layout | Layout
Each directory in `ocean-src` is a package, imported by its path from the repository root: the `term/tui` directory is imported as `"term/tui"`. There is no build step: the compiler reads the library's source whenever a program imports it, so you edit `.oc` files and use them immediately.

Packages whose implementation differs between native targets and WebAssembly use `_native.oc` and `_wasm.oc` files. Differences between operating systems and CPUs are handled with inline assembly blocks selected by architecture and platform, which is how `io`, `os`, `time`, and `term` make system calls. Code that needs to know the target at run time calls `os.OS()` and `os.Arch()`.

Calls into the C library and Win32, such as `stat` or `GetFileAttributesW`, go through `internal/native`, a private package of small assembly bridges for every target. Its `native.oc` is generated: add a function to the table in `internal/native/generate.py` and run `python3 internal/native/generate.py`. A bridge takes at most three arguments, and on targets that lack the function it returns -1. Likewise, `unicode/tables.oc` is generated by `unicode/generate_tables.py`.

--- testing | Testing a change
Point a matching compiler at your checkout with `OCEAN_SRC`, then run the Ocean unit tests from the repository root. Tests live next to the code in `_test.oc` files.
```code Terminal
export OCEAN_SRC="$PWD"
ocean test ./... --notty
ocean test encoding/json io
```
@after
The HTTP tests need permission to open local sockets; they don't contact outside servers. A few packages also have Python harnesses for behavior that needs a real terminal or several processes, in `term/tests`, `term/tui/tests`, `threads/tests`, `time/tests`, `os/signal/tests`, and similar directories. Set `OCEAN` to the compiler to use when running them.

--- conventions | Conventions
Exported names start with an uppercase letter and the rest stay private. Recoverable failures are returned as `Result<T>`; panics are reserved for misuse, such as invalid arguments. Each package directory has a `README.md` describing its API and behavior; keep it up to date along with these website pages.

The `reflect` package is special: it can call compiler primitives that no other package may use, and only when it lives in the configured standard-library directory.

=== contribute/website
group: Contribute
title: Working on the website
desc: Run this website locally, edit documentation pages, and verify their examples.

--- setup | Run the site locally
The website is built with SvelteKit and Svelte 5 and deployed to Cloudflare Workers. Install Node.js and npm, then install the locked dependencies, generate the Cloudflare types, and start the development server.
```code Terminal
npm ci
npm run gen
npm run dev
```

--- content | Where the documentation lives
Each documentation page is written in a plain-text file in `content/docs/`. Pages appear in the order of the files, sorted by name, and in their order within each file. The script `scripts/build_docs.py` turns these files into `src/lib/docs.ts`, which the site reads to build every page, the sidebar, search, and the previous and next links. Don't edit `docs.ts` by hand; edit the text files and run `npm run docs`.

--- format | The page format
A page starts with `===` and its URL slug, followed by its group, title, and description. Each section starts with `---`, an identifier, and a title. Plain lines are the section's text; a blank line starts a new paragraph, and backticks mark inline code. A section may contain one code block, written between a line starting with three backticks and the word `code` and a closing line of three backticks, optionally labeled after `code`. After the code block, `@after` begins text shown below the example, `@note` a highlighted callout, `@table` a table (first row is the header, cells separated by `|`, written as `\|` inside a cell), and `@links` a list of `Label -> URL` lines.
```code Page source
=== language/example
group: Language guide
title: Example page
desc: One sentence describing the page.

--- intro | Introduction
Text with `inline code`.

A second paragraph.
@note
A callout.
```
@after
Groups must be one of the groups listed in the script. Markdown other than inline code is shown literally, so use `@links` rather than Markdown link syntax.

--- examples | Verify the examples
`scripts/check_docs.py` compiles every complete Ocean example (any example containing a `package` declaration) with `ocean check`. It uses the `ocean` on your `PATH`, or the compiler named by the `OCEAN` environment variable, and the usual `OCEAN_SRC` setting to choose the library. Lines that control the checker are removed from the published page: `// check: run` runs the example instead of only checking it, each `// expect: TEXT` line gives one expected line of output, `// check: skip` excludes an example that needs input or a network, and `// file: path` splits an example into several files.
```code Terminal
python3 scripts/check_docs.py content/docs
OCEAN=../ocean/build/ocean OCEAN_SRC=../ocean-src \
  python3 scripts/check_docs.py content/docs language/functions
```

--- validate | Check and build
Run the type checks and a production build before submitting a change, and look over the changed pages in `npm run preview` at both desktop and phone widths.
```code Terminal
npm run docs
npm run check
npm run build
```
